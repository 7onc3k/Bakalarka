\section{Kvalita software a~její měření}
\label{sec:swe-zivotni-cyklus}
%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%%

Softwarové inženýrství k~vývoji softwaru přistupuje systematicky:
od specifikace přes implementaci po údržbu~\cite{swebok2024}.
Jedním z~jeho úkolů je zajištění kvality výsledku~\cite{sommerville2016},
a~právě otázka, co se kvalitou rozumí a~jak ji měřit, určuje, jaké
metriky lze pro práci coding agenta vůbec navrhnout. Než se proto
v~kapitole~\ref{kap:metodika} pustíme do konkrétních metrik, je
třeba vymezit, na~čem se kvalita v~softwarovém inženýrství měří.

Kvalita se přitom v~literatuře neredukuje na vlastnost hotového
produktu. Fenton a~Bieman~\cite{fenton2014} rozlišují tři kategorie
měřitelných entit:
\begin{itemize}
    \item \textit{produkt}, tedy výstupy vývoje (implementace,
          testy, dokumentace),
    \item \textit{proces}, tedy aktivity a~postupy, kterými
          produkt vzniká,
    \item \textit{zdroje}, tedy vstupy nutné k~jeho vzniku (čas,
          úsilí, lidé, výpočetní prostředky).
\end{itemize}
\label{sec:mereni-kvality-obecne}%
\label{sec:mereni-kvality}%
Každá entita nese jiný typ evidence o~kvalitě, a~ucelený obraz
proto vzniká až jejich kombinací. Funkčně správný produkt může
vzniknout chaotickým procesem, dodržení procesu zase nezaručuje
funkční výsledek, a~náklady, za které řešení vzniklo, jsou na obou
předchozích nezávislé.

Následující tři podsekce rozebírají každou dimenzi zvlášť: její
konceptuální vymezení a~způsoby, jimiž ji literatura
operacionalizuje. Hloubka zpracování se mezi dimenzemi liší a~tato
asymetrie odráží stav literatury, ne výběr autora. Produktová
stránka má dnes zralý standardizovaný rámec
(sekce~\ref{sec:produktova-kvalita}). Procesní stránka stojí na
rodině etablovaných praktik vývoje software
(sekce~\ref{sec:procesni-kvalita}). Zdrojová dimenze se zachycuje
převážně přes proxy nákladů, úsilí a~času
(sekce~\ref{sec:zdrojova-dimenze}).

\subsection{Produktová kvalita}
\label{sec:produktova-kvalita}
\label{sec:dimenze-kvality}
\label{sec:testovani-mutation}
\label{sec:staticka-analyza}
\label{sec:definice-komplexita}

SWEBOK definuje kvalitu software jako míru, do jaké splňuje
stanovené požadavky a~odpovídá potřebám stakeholderů, pro které byl
vytvořen~\cite{swebok2024}. Tyto potřeby ale nejsou jednotné.
Koncový uživatel a~zadavatel především chtějí, aby software dělal
to, co má, spolehlivě a~bezpečně. Vývojář a~maintainer naopak
hodnotí, zda je systém srozumitelný, modifikovatelný a~dlouhodobě
udržitelný~\cite{sommerville2016}. Software, který splňuje funkční
požadavky, může být přesto obtížně čitelný a~náchylný k~chybám
při úpravách. Jediné měřítko proto nestačí, a~modely kvality právě
z~tohoto důvodu rozkládají kvalitu produktu do více dílčích
charakteristik, které lze posuzovat odděleně.

Standardizovaným rámcem produktové kvality je dnes
ISO/IEC~25010~\cite{iso25010}, navazující na starší modely jako
McCallův z~roku 1977~\cite{mccall1977}. Současný model dělí kvalitu
produktu do osmi charakteristik: funkční vhodnost, výkonnostní
efektivita, kompatibilita, použitelnost, spolehlivost, bezpečnost,
udržovatelnost a~přenositelnost. Pro hodnocení coding agenta je
tento rozklad důležitý tím, že odděluje otázku, zda software dělá
to, co se od něj očekává, od otázky, zda je jeho kód vhodný pro
další rozvoj. Z~osmi charakteristik proto v~literatuře o~generování
kódu stojí do popředí dvě, které tomuto rozdělení přímo odpovídají.

\textit{Funkční vhodnost} vyjadřuje, do jaké míry software poskytuje
funkce naplňující stanovené potřeby za specifikovaných
podmínek~\cite{iso25010}, a~projevuje se v~chování programu za
běhu vůči specifikaci. \textit{Udržovatelnost} vyjadřuje, s~jakou
účinností lze software upravovat při opravách, zlepšeních nebo
přizpůsobování změnám~\cite{iso25010}, a~projevuje se naopak ve
vlastnostech zdrojového kódu, nikoli až za běhu. V~kontextu coding
agentů se první charakteristika vztahuje k~tomu, zda agent vytváří
správné řešení, zatímco druhá k~tomu, zda jeho kód lze dále chápat,
upravovat a~rozvíjet. Obě tedy vyžadují odlišné typy evidence:
funkční vhodnost se ukazuje za běhu, udržovatelnost při čtení kódu.
Přehled a~srovnání produktových modelů kvality podává Miguel
et al.~\cite{miguel2014}.

\paragraph{Proč je dosažení kvality obtížné.}
Modely kvality vymezují, jaké vlastnosti od software očekáváme,
neříkají ale, proč je jejich dosažení v~praxi obtížné.
Brooks~\cite{brooks1987} tento problém otevírá rozlišením dvou
druhů složitosti. \textit{Esenciální složitost} je vlastní řešenému
problému a~nelze ji odstranit lepšími nástroji, lze ji pouze
pochopit a~strukturovat. \textit{Akcidentální složitost} naopak
do systému vnáší zvolené technologie a~implementační rozhodnutí,
jako jsou konfigurace frameworku, řešení verzí závislostí nebo
nastavení build systému. Pro hodnocení coding agenta je toto
rozlišení důležité, protože jeho výstupy stojí na obojím. Část
úsilí je nutně věnována podstatě úlohy, zbytek tomu, jak se agent
vypořádá s~prostředím a~konvencemi konkrétního projektu, a~právě
tato akcidentální část bývá zdrojem rozdílu mezi povrchně funkčním
a~skutečně udržitelným řešením.

\paragraph{Testování.}
Funkční vhodnost se ověřuje testováním, tedy systematickou kontrolou
chování implementace vůči očekávání odvozenému ze specifikace nebo
akceptačních kritérií. Význam testování spočívá v~tom, že chyby
zachytí dříve, než se projeví v~provozu, kdy je jejich oprava
řádově dražší.

V~praxi se testy organizují do tří úrovní podle rozsahu kódu, který
ověřují. \textit{Unit testy} ověřují jednotlivé funkce nebo moduly
izolovaně a~slouží především k~rychlé zpětné vazbě během vývoje.
\textit{Integrační testy} ověřují spolupráci komponent a~zachycují
chyby na rozhraních, které izolovaný unit test odhalit nemůže.
\textit{Akceptační testy} ověřují splnění požadavků z~pohledu
zadavatele a~vypovídají o~tom, zda software dělá to, co od něj
zadavatel skutečně očekával. Každá úroveň zachycuje jiný typ chyb
a~v~praxi se používají v~kombinaci.

Samotný průchod testů ovšem vypovídá primárně o~testované
implementaci, nikoli o~síle testů samotných. První vrstvou hodnocení
testovací sady je strukturální coverage (\textit{line},
\textit{branch}), která ukazuje, jak velkou část kódu testy vykonaly.
Coverage sama o~sobě ale neříká, zda by testy skutečnou chybu
zachytily, protože vykonaný řádek bez vhodné aserce projde i~tehdy,
když implementace dělá něco zcela jiného, než má~\cite{papadakis2019}.
\textit{Mutation testing} tuto slabinu doplňuje druhým pohledem,
sílou testovací sady. Do programu systematicky zavádí drobné změny
(\textit{mutanty}), které simulují běžné programátorské chyby,
a~sleduje, kolik z~nich testy odhalí~\cite{papadakis2019}. Vysoká
míra zachycených mutantů indikuje, že testy skutečně ověřují
chování, ne jen pokrývají kód.

\paragraph{Statická analýza a~konvence kódu.}
Udržovatelnost se na rozdíl od funkční vhodnosti neprojevuje za
běhu, ale ve vlastnostech zdrojového kódu, takže její část lze
hodnotit i~bez spuštění programu. Statická analýza pro tento účel
nabízí proxy metriky vybraných vnitřních atributů a~slouží jako
časný signál strukturálních problémů.

Cyklomatická složitost~\cite{mccabe1976} vyjadřuje počet lineárně
nezávislých cest grafem řízení toku jedné funkce a~používá se jako
jednoduchý ukazatel její srozumitelnosti. Vyšší hodnoty souvisejí
s~vyšší chybovostí a~nižší testovatelností, v~praxi se proto často
udržuje práh~10 na funkci~\cite{mcconnell2004}. Linting kontroluje
porušení jazykových a~projektových konvencí a~typová kontrola
zachycuje nekonzistence v~rozhraních a~práci s~datovými typy ještě
před spuštěním programu.

Strukturální nástroje ale pokrývají jen ty aspekty udržovatelnosti,
které lze formálně vyjádřit pravidlem. V~praxi se udržovatelnost
dál opírá o~vlastnosti jako čitelnost, srozumitelné pojmenování,
oddělení zodpovědností nebo dodržování konvencí
jazyka~\cite{mcconnell2004}, jež vznikají průběžným refaktoringem
a~důslednou prací s~rozhraními a~odpovědnostmi modulů. SWEBOK
zdůrazňuje, že úroveň udržovatelnosti neposilují jen vlastnosti
samotného kódu, ale i~systematické vývojové procesy, techniky
a~nástroje, které jeho vznik provázejí~\cite{swebok2024}.

\paragraph{Meze deterministického hodnocení.}
Vhodnost dekompozice, přiměřenost návrhových rozhodnutí nebo
sémantická srozumitelnost přesahují možnosti čistě deterministických
nástrojů, protože vyžadují posouzení záměru, kontextu a~čitelnosti
z~pohledu jiného vývojáře. K~těmto vlastnostem se v~literatuře
přistupuje přes expertní hodnocení, jehož operacionalizace
v~kontextu coding agentů je předmětem
kapitoly~\ref{kap:metodika}.

\subsection{Procesní kvalita}
\label{sec:procesni-kvalita}
\label{sec:praktiky-kvality}
\label{sec:faze-zivotniho-cyklu}

Procesní kvalita se neprojevuje na hotovém produktu, ale v~tom,
jak vznikal. Fenton a~Bieman~\cite{fenton2014} mezi procesní
atributy řadí zejména efort, trvání, shodu s~definovaným postupem
a~stabilitu výstupu, tedy vlastnosti, které lze pozorovat
na chování vývojáře, ne na hotovém kódu.

Procesní praktiky určují, jak změny vznikají, kontrolují se
a~začleňují do projektu. Jejich dodržování zvyšuje auditovatelnost
i~spolehlivost vývoje, protože poskytuje strukturu, ve které lze
zpětně rekonstruovat, jak ke každé změně došlo. Pro hodnocení
coding agenta to znamená, že nestačí se ptát, zda jeho výstup
funguje, ale i~jakým postupem ke kódu dospěl a~zda tento postup
splňoval zavedené standardy oboru.

\paragraph{Správa verzí, integrace a~traceability.}
Základem pozorovatelnosti procesu je správa verzí, která umožňuje
sledovat historii změn a~bezpečně se vracet k~předchozím stavům
kódu. Pro kvalitu vývoje není rozhodující samotný nástroj, ale
způsob, jakým se používá. Práce v~oddělených větvích
(\textit{branches}) izoluje rozpracované změny od stabilního kódu
a~umožňuje paralelní práci bez vzájemného rušení. Shihab
et al.~\cite{shihab2012} empiricky ukázali, že nesoulad mezi
strukturou větví a~organizační strukturou je spojen s~vyšší mírou
defektů po vydání, což naznačuje, že strategie větvení nese
informaci o~zdraví procesu, nejen o~organizaci práce.

Granulární commity, kde každá změna odpovídá jednomu logickému
kroku, usnadňují zpětnou analýzu chyb i~code review, protože
reviewer vidí menší a~lépe ohraničené změny~\cite{humble2010}.
Průběžná integrace (\textit{continuous integration}) tyto praktiky
doplňuje automatickým ověřováním, že sloučení změn nenarušilo
funkčnost. Rychlá zpětná vazba snižuje cenu pozdního odhalení
chyby~\cite{humble2010}.

Vedle správy verzí a~integrace je pro kvalitu vývoje důležitá také
\textit{traceability}, schopnost dohledat vazby mezi požadavkem
a~artefakty, které s~ním souvisejí~\cite{gotel1994}. Nejde jen
o~uchování historie kódu, ale o~propojení zadání změny, její
implementace, review a~ověření. V~praxi to znamená vazby mezi
issue, commity a~větvemi, pull requestem a~testy. Díky nim lze
zpětně pochopit, proč byla změna provedena, co přesně měnila a~jak
bylo ověřeno, že odpovídá zadání.

\paragraph{Test-driven development.}
Testování v~průběhu implementace může mít různé pořadí, a~zvolené
pořadí mění roli, kterou test ve vývoji hraje. Nejběžnější je
\textit{test-after} přístup, kdy vývojář napíše implementaci
a~následně k~ní vytvoří testy ověřující, že implementace dělá to,
co zamýšlel. \textit{Test-driven development} pořadí obrací:
nejprve se napíše test definující očekávané chování, teprve pak
implementace, která test splní~\cite{beck2000}. Tím se test stává
specifikací požadavku, nikoli zpětnou kontrolou již napsaného kódu,
a~vývojář je nucen vyjádřit záměr ještě před tím, než ho začne
realizovat.

Meta-analýza 27~studií Rafiqueho a~Mišiće~\cite{rafique2013}
ukazuje, že TDD má pozitivní efekt na kvalitu kódu měřenou hustotou
defektů. Efekt je výraznější v~průmyslových projektech než
v~akademických experimentech, což naznačuje, že přínos roste
se složitostí řešeného problému, kde je explicitní specifikace
chování nejcennější.

\paragraph{Code review.}
Kontrolu změn před začleněním strukturuje code review, kontrola
kódu jiným vývojářem před jeho začleněním do hlavní vývojové větve.
Historicky probíhala formou strukturovaných inspekcí, dnes převládá
méně formální podoba integrovaná do pull requestů, označovaná jako
\textit{modern code review}. Jde o~průběžné posuzování menších změn
jako běžné součásti integrace, nikoli o~samostatnou formální
inspekci celé implementace.

Jeho současnou průmyslovou podobu popisují Bacchelli a~Bird na
datech Microsoftu~\cite{bacchelli2013} a~Sadowski et al. na datech
Google~\cite{sadowski2018codereview}. Obě studie ukazují, že modern
code review je dnes v~průmyslu adoptovanou praktikou napříč
organizacemi různé velikosti. Kromě odhalování defektů přispívá
review ke sdílení znalostí v~týmu, k~nalézání alternativních
řešení a~k~udržování konzistence stylu napříč codebase.
McIntosh et al.~\cite{mcintosh2016} dále empiricky prokázali, že
kód, který neprošel review, vykazuje měřitelně vyšší míru defektů
po vydání, což hodnotu této praktiky kvantifikuje.

\paragraph{Diagnostika chyb.}
Diagnostika chyb tvoří průřezovou praktiku, která se uplatňuje
kdykoli implementace selže nebo se chová jinak, než vývojář
očekával. Její význam spočívá v~tom, že rozhoduje, zda se chyba
opraví trvale (analýzou skutečné příčiny), nebo jen zamaskuje
úpravou symptomu, který se po čase vrátí v~jiné podobě.

Zralá praxe se proto opírá o~systematickou analýzu příčin místo
spoléhání na první nápad. Ko a~Myers~\cite{komyers2008debugging}
ve studii vývojářského debuggingu empiricky ukazují, že první
odhad příčiny je často nesprávný, a~vývojáři, kteří přeskočí
ověření hypotézy, opakovaně končí u~úpravy špatného místa kódu.
Explicitní postup, tedy formulace hypotézy o~příčině, její ověření
a~teprve následný zásah, je proto součástí zavedeného repertoáru
SE praktik a~projevuje se v~pozorovatelných artefaktech jako
diagnostické commity, dočasné logy nebo testovací reprodukce
chyby před opravou.

\paragraph{Deklarace versus pozorovaná praxe.}
Existence praktiky v~repertoáru oboru ještě neznamená, že je
v~konkrétním projektu skutečně dodržována. Zda se TDD, code review
nebo systematická diagnostika reálně provádějí, je empirická otázka,
nikoli věc deklarace v~dokumentaci nebo metodice projektu.

Rozsáhlá field study Bellera et al.~\cite{beller2019testing}
sledovala 2\,443~vývojářů v~IDE po dobu 2,5~roku napříč čtyřmi
nástroji. Výsledky ukazují, že polovina vývojářů systematicky
netestuje, TDD není rozšířené ani v~komunitě, která se k~němu hlásí,
a~čas strávený testováním je výrazně nižší než ten, který si
vývojáři sami přisuzují. Procesní charakteristiky je proto vhodné
hodnotit z~pozorovatelných artefaktů vývoje, jako jsou commity,
pull requesty nebo záznamy z~CI, nikoli z~deklarovaného postupu.
Tento princip přímo ovlivňuje volbu procesních metrik, k~níž se
vrací kapitola~\ref{kap:metodika}.

\paragraph{Rámce procesní zralosti.}
Vedle pozorovatelných praktik existují organizační rámce procesní
zralosti, zejména CMM/CMMI~\cite{paulk1993cmm}
a~ISO/IEC~33020~\cite{iso33020}. Ty popisují pětistupňovou škálu
zralosti procesu napříč organizací a~slouží k~auditu a~certifikaci
celých vývojových útvarů. Jejich horizont je dlouhodobý
a~agregovaný, hodnotí, jak organizace své procesy definuje, řídí
a~zlepšuje napříč mnoha projekty a~roky. Pro pozorování jednoho
experimentálního běhu (například běhu coding agenta nad jednou
sadou úloh) tyto rámce neposkytují přímo použitelné metriky, protože
operují na úplně jiné jednotce analýzy.

\subsection{Zdrojová dimenze}
\label{sec:zdrojova-dimenze}
\label{sec:modely-metodiky}

Zdrojová dimenze zachycuje náklady, za které výsledek vzniká.
Fenton a~Bieman~\cite{fenton2014} mezi zdrojové atributy řadí
zejména čas, lidské úsilí a~použití výpočetních prostředků. Na
rozdíl od produktové stránky, kde existují standardizované modely
kvality, a~procesní stránky, kde je základem rodina etablovaných
praktik, zdrojová dimenze se v~literatuře zachycuje převážně přes
proxy měření, a~právě tato proxy povaha ji odlišuje od obou
předchozích.

\paragraph{Tradiční proxy a~odhady pracnosti.}
K~odhadu pracnosti a~nákladů softwarového projektu se v~tradičním
SE používají kvantitativní modely. \textit{COCOMO} (Constructive
Cost Model) odhaduje pracnost na základě velikosti projektu (SLOC)
a~násobných efektových faktorů~\cite{boehm1981cocomo}. V~agilním
vývoji jej doplňují odhadovací techniky typu story points
a~planning poker, které pracují s~relativní pracností místo
absolutních hodin. Vedle odhadu se měří i~průběh vývoje, typicky
přes osobohodiny strávené nad úkolem, \textit{cycle time} (dobu od
začátku práce po nasazení) nebo \textit{lead time} (dobu od
požadavku po doručení).

\paragraph{Produktivita jako multi-dimenzionální veličina.}
Samotné úsilí ani počet výstupů ovšem nevypovídá o~tom, zda je
vývoj efektivní, a~jednorozměrné metriky typu SLOC za hodinu mohou
být zavádějící. Forsgren, Humble a~Kim~\cite{forsgren2018}
v~rámci DORA (DevOps Research and Assessment) empiricky argumentují,
že výkon týmu zachycují čtyři metriky: frekvence nasazení, lead
time změn, míra selhávajících změn a~čas na obnovu po výpadku. Pro
individuálního vývojáře navazující SPACE
framework~\cite{forsgren2021space} rozšiřuje pohled na pět os
(\textit{Satisfaction}, \textit{Performance}, \textit{Activity},
\textit{Communication}, \textit{Efficiency}) a~explicitně varuje
před redukcí produktivity na jedinou metriku typu SLOC nebo počet
commitů. Tento princip více os se přenáší i~do hodnocení agentních
systémů, kde samotná úspěšnost na úloze nevypovídá o~nákladech ani
o~kvalitě procesu.

\paragraph{Od lidských hodin k~tokenům.}
U~coding agentů mění tyto proxy podobu, ale jejich logika zůstává
stejná. Osobohodiny nahrazují spotřebované tokeny a~wall-clock
čas na úlohu, místo lidské únavy vystupuje rate limit jako vzácný
zdroj omezující propustnost. Vztah mezi náklady a~výsledkem se
nemění, mění se jen jeho konkrétní podoba, a~rozbor
agent-specifických proxy je předmětem
sekce~\ref{sec:agenti-meni-sdlc}.

\textbf{Zachovaný text původní 2.1.3 (finální verze 2026-04-24):}

\textit{Předchozí sekce identifikovala praktiky, kterými se kvalita
software zajišťuje. Samotná existence praktik však neznamená, že se
dodržují, ani že jejich výstupy jsou kvalitní. Kvalitu je proto
třeba měřit.}

\textit{Fenton a~Bieman rozlišují tři kategorie měřitelných entit
v~softwarovém inženýrství: proces (aktivity během vývoje), produkt
(výstupy vývoje) a~zdroje (lidé, nástroje, výpočetní kapacita).}

\textit{Produktové měření: funkční vhodnost znamená shodu chování
implementace se specifikací; testování je způsob zjištění této
shody. Testovací sada je samostatný produktový artefakt; její síla
se neodvozuje jen z~průchodu testů. Strukturální coverage (line,
branch) ukazuje, jakou část kódu testy vykonaly, ale neříká, zda
by zachytily skutečnou chybu (Papadakis et al.\ 2019). Mutation
testing coverage doplňuje o~měření síly testovací sady.}

\textit{Udržovatelnost se projevuje ve vlastnostech zdrojového
kódu. Statická analýza hodnotí kód bez spuštění: cyklomatická
složitost (McCabe 1976) vyjadřuje počet lineárně nezávislých cest
grafem řízení toku, v~praxi práh~10 na funkci (McConnell 2004).
Linting a~typová kontrola zachycují porušení konvencí
a~nekonzistence. Statická analýza je pouze proxy pro vybrané
atributy udržovatelnosti; vhodnost dekompozice, pojmenování nebo
přiměřenost návrhových rozhodnutí přesahují možnosti čistě
deterministických nástrojů.}

\textit{Procesní měření sleduje, zda praktiky skutečně proběhly
a~zda jejich artefakty (commity, issues, pull requesty, záznamy
z~CI) nesou požadovanou strukturu a~kvalitu.}

\textit{Měření zdrojů: v~tradičním SE čas, lidské úsilí, použití
nástrojů a~výpočetních prostředků. U~AI coding agentů se projevuje
v~čase běhu, spotřebovaných tokenech, použití nástrojů a~stabilitě
session.}

\subsection{Základní pojmy a~typy}
\label{sec:zakladni-pojmy}
\label{sec:typy-coding-agentu}

\textit{Velký jazykový model} (\textit{large language model}, LLM)
je neuronová síť trénovaná na rozsáhlých textových
korpusech~\cite{vaswani2017}. Na základě předchozího kontextu
predikuje pravděpodobný následující token, a~tím generuje koherentní
text, včetně zdrojového kódu. Samotný LLM je však pasivní: odpovídá
na dotazy, ale nemůže samostatně číst soubory, spouštět příkazy
ani měnit stav projektu.

\textit{LLM-based agent} model rozšiřuje o~schopnost interagovat
s~prostředím~\cite{liu2024llmagents}: plánuje kroky, volá nástroje
(\textit{tool use}~\cite{schick2023toolformer}) a~na základě pozorovaného
výsledku rozhoduje o~dalším kroku v~cyklu
Thought~$\to$~Action~$\to$~Observation~\cite{yao2022react}. V~kontextu
softwarového vývoje to znamená, že agent může číst a~zapisovat
soubory, spouštět testy, používat verzovací systém nebo volat API.
Právě tyto schopnosti určují, jak agent zpracuje instrukce a~jaké
měřitelné stopy po sobě zanechá.

Předmětem této práce jsou \textit{autonomní coding agenti}, tedy
systémy, které na základě specifikace a~instrukcí samostatně
implementují softwarový projekt (např.\ Claude Code, OpenHands)~\cite{guo2025benchmarks}.
Na rozdíl od asistenčních nástrojů (GitHub Copilot) agent provádí celý
vývojový proces, nikoli jen jednotlivé kroky. Jeho výstupy proto lze
posuzovat stejnými požadavky na kvalitu procesu i~produktu, jaké
popisuje sekce~\ref{sec:swe-zivotni-cyklus}.

\subsection{Jak agenti mění softwarové inženýrství}
\label{sec:agenti-meni-sdlc}

Přechod od lidského vývojáře k~autonomnímu agentovi posouvá
softwarové inženýrství ve všech třech dimenzích zavedených
v~sekci~\ref{sec:mereni-kvality-obecne}. Jin
et al.~\cite{jin2024llmagents} v~přehledu 124 studií ukazují, že
agenti pronikají do šesti oblastí SE: požadavků, generování kódu,
autonomního rozhodování, návrhu, generování testů a~údržby.
Důsledky pro každou dimenzi měření kvality se však liší.

Procesní stránka se mění v~tom, kdo provádí jednotlivé kroky,
a~v~tom, jakou stopu po sobě zanechávají. Agenti fungují jako
sekvence cyklu Thought--Action--Observation~\cite{yao2022react}
nad sandboxovaným prostředím: čtou a~upravují repozitář, spouští
testy a~skripty, komitují a~otevírají pull requesty. Open-source
implementace jako SWE-agent~\cite{yang2024sweagent} ukazují, že
i~drobné úpravy rozhraní mezi agentem a~prostředím (agent-computer
interface) posouvají úspěšnost na reálných úlohách o~jednotky
procentních bodů. V~produkčním nasazení tak vzniká procesní stopa
v~podobě commitů, větví a~CI výstupů, kterou lze zpětně analyzovat;
empirická pozorování ale ukazují, že agent-generované pull requesty
se od těch lidských liší mírou nadbytečnosti, konzistencí commit
zpráv a~ochotou reviewera je přijmout~\cite{watanabe2025agentprs,
ehsani2026failedprs}.

Produktová stránka zůstává vymezena stejnými charakteristikami
(viz sekce~\ref{sec:dimenze-kvality}), ale typické vzorce
agent-generovaného kódu jsou jiné než u~lidského vývojáře.
Li et al.~\cite{li2026beyondbugfixes} na 1210~merged agent-PR
z~reálných repozitářů zjistili, že i~přijaté patche nesou vyšší
výskyt code smells, duplikací a~strukturálních problémů, které
merge samotný neodhalí. Zhodnocení výstupu proto v~literatuře
kombinuje automatizované benchmarky
(sekce~\ref{sec:hodnoceni-ai-agentu}) s~post-hoc statickou analýzou
a~s~hodnocením od LLM-judgů či lidských reviewerů.

Zdrojová stránka dostává u~agentů nové proxy. Na místě člověko-hodin
stojí spotřebované tokeny a~čas běhu na úlohu; kontextové okno
a~rate limit vystupují jako vzácné zdroje, které ovlivňují, kolik
úloh a~jak dlouhých agent zvládne. Empirické práce v~této
oblasti ukazují, že řízení kontextu samo o~sobě významně mění
ekonomiku běhu: například Lindenbauer et al.~\cite{jetbrains2025complexity}
pozorují, že jednoduché maskování pozorování dosáhne srovnatelné
úspěšnosti jako LLM-sumarizace za polovinu nákladů.

Protože běžné benchmarky hodnotí izolované úlohy a~zavedené
rámce (ISO~25010 pro produkt, CMMI/ISO~33020 pro proces) nepokrývají
všechny tři dimenze v~režimu jednoho experimentálního běhu, je
pro vyhodnocení coding agenta v~rámci jedné case study třeba
operacionalizovat všechny tři dimenze cíleně. Tento krok řeší
kapitola~\ref{kap:metodika}.

\subsection{Instrukce jako nezávislá proměnná}
\label{sec:scaffolding}
\label{sec:problem-kontextu}
\label{sec:pristupy-memory}
\label{sec:scaffolding-instrukce}

Autonomní agent nemá \textit{tacit knowledge}, tedy implicitní znalosti, které
lidský vývojář získává zkušeností: jaké konvence tým dodržuje, proč
je kód strukturovaný určitým způsobem nebo jaké chyby se v~projektu
opakují. Nonaka a~Takeuchi~\cite{nonaka1995} popisují převod tacit
knowledge na explicitní jako klíčový proces v~organizacích. Pro
agenty je tento převod nutný v~plném rozsahu: veškerý kontext, který
agent potřebuje, musí být zapsán explicitně. Hassan
et al.~\cite{hassan2025sase} tuto dualitu formalizují v~rámci SASE
(\textit{Software Engineering for Agents}): zatímco lidský vývojář
(SE4H) čerpá z~meetingů, code review a~zkušenosti, agent (SE4A)
pracuje výhradně s~tím, co dostane jako vstup.

\textit{Scaffolding} označuje strukturované artefakty v~prostředí
agenta, které jeho chování řídí. V~praxi jde nejčastěji
o~instrukční soubory umístěné v~repozitáři
(např.\ \texttt{AGENTS.md}, \texttt{CLAUDE.md}), které definují
roli agenta, pracovní postup, konvence a~omezení. Na rozdíl od
jednorázových promptů jsou tyto soubory verzované a~iterativně
upravované, což z~nich činí ``living documents,'' jejichž vývoj
lze zpětně sledovat.

Mao et al.~\cite{mao2025fse} analyzovali 2\,163 produkčních
prompt šablon a~identifikovali sedm typů komponent: Role,
Directive, Context, Workflow, Output, Constraints a~Examples.
Zjistili, že Role a~Directive se nejčastěji objevují na začátku
dokumentu a~že Workflow (procedurální kroky) je nejúčinnější
komponentou pro složité úkoly. Toto zjištění potvrzují Li
et al.~\cite{skillsbench2025}, kteří ukazují, že procedurální
instrukce (``jak pracovat'') jsou efektivnější než popisná
dokumentace (``jak vypadá codebase'').

Empirická evidence o~účinnosti instrukčních souborů je smíšená
a~ukazuje, že samotná přítomnost instrukcí nestačí: rozhodující je
jejich obsah, struktura a~relevance pro konkrétní úlohu. Přítomnost
souboru \texttt{AGENTS.md} je sice spojena s~nižší mediánovou dobou
běhu agenta ($-28{,}6\,\%$)~\cite{lulla2026}, ale dopad závisí na
původu obsahu: LLM-generované instrukční soubory úspěšnost agenta
snižují a~i~soubory napsané vývojáři přinášejí jen marginální
zlepšení~\cite{gloaguen2025agentsmd}. V~benchmarku SkillsBench
zlepšují kurátorované moduly výsledky o~16,2~procentních bodů,
zatímco automaticky generované nemají žádný
efekt~\cite{skillsbench2025}. Účinnost jednotlivých typů obsahu
přitom dosud nebyla izolována.

Chování agenta je navíc citlivé na formulaci instrukcí. Breunig
et al.~\cite{breunig2025} ukazují, že přestrukturování instrukce
je účinnější než její opakování: když agent pravidlo ignoruje,
nepomůže ho zopakovat; je třeba ho přeformulovat tak, aby se stalo
součástí pracovního postupu. Razavi a~Fard~\cite{razavi2025}
dokládají, že drobné změny formulace promptu mohou dramaticky
změnit chování modelu, což motivuje cílené úpravy místo přidávání
dalších pravidel.

Na chování agenta působí také \textit{specificita} instrukce.
Kim et al.~\cite{kim2025detail} v~benchmarku DETAIL a~Zi
et al.~\cite{zi2025specificity} na úlohách s~kódem shodně ukazují,
že konkrétnější formulace zvyšují úspěšnost agenta, ale přílišný
detail může omezit jeho reasoning. Instrukce se tak pohybují po
ose od volné nápovědy po explicitní příkaz, přičemž optimální
bod závisí na úloze i~modelu.

Výzkum promptingu navíc naznačuje, že instrukce nepůsobí na chování
modelu jedním mechanismem. Wei et al.~\cite{wei2022cot} ukazují, že
i~krátká nápověda (``think step by step'') aktivuje reasoning, který
se bez ní neprojeví, a~Min et al.~\cite{min2022rethinking} dokládají,
že demonstrace v~in-context learning působí spíš jako strukturální
vodítka než jako přímé příkazy. Chování modelu lze tedy ovlivnit
přímým \textit{vynucením} i~\textit{aktivací} latentních znalostí;
která z~cest je v~konkrétním případě účinnější, nelze rozhodnout
předem.

Otevřenou otázkou proto není jen to, zda instrukce obecně pomáhají,
ale jak jejich obsah systematicky navrhovat a~jak poznat, které
složky skutečně mění chování agenta.

\subsection{Hodnocení schopností agentů}
\label{sec:hodnoceni-ai-agentu}
\label{sec:evaluace-agentu-instrukci}
\label{sec:hodnoceni-agentu}
\label{sec:evaluace-instrukci}
\label{sec:llm-as-judge}

De facto standardem pro hodnocení coding agentů je
SWE-bench~\cite{swebench2024}: benchmark obsahující 2\,294 úloh
z~reálných GitHub repozitářů, kde agent dostane popis problému
(GitHub issue) a~má vytvořit patch, který projde testy. Hodnocení
je binární: patch projde nebo neprojde. Obdobně
HumanEval~\cite{chen2021humaneval} měří schopnost modelu generovat
funkčně správný kód na izolovaných programovacích úlohách.

Tyto benchmarky měří \textit{funkční korektnost}: zda výsledek dělá
to, co má. Neměří však, jak agent pracoval (dodržoval proces?),
jakou strukturální kvalitu má výsledný kód (je udržovatelný?) ani za
jakou cenu výsledku dosáhl (kolik tokenů spotřeboval?).
Kapitola~\ref{kap:vymezeni} tuto mezeru dokládá na třech nezávislých
empirických studiích (METR~\cite{metr2026}, Li
et al.~\cite{li2026beyondbugfixes} a~Ehsani
et al.~\cite{ehsani2026failedprs}), které na různě velkých vzorcích
a~z~různých úhlů ukazují, že pass/fail výsledek samotný neodpovídá
praktické použitelnosti patche: nezachycuje code review, udržovatelnost
ani procesní integritu. Každá studie pojmenovává jinou stranu téhož
problému.

Existují benchmarky, které hodnocení rozšiřují nad rámec pass/fail.
SWE-bench Pro~\cite{swebenchpro2025} přidává strukturované
požadavky, ACE-Bench~\cite{acebench2025} testuje end-to-end vývoj
a~FeatureBench~\cite{featurebench2026} hodnotí implementaci celých
funkcí. Žádný z~nich však systematicky neměří kvalitu procesu (jak
agent organizoval práci), kvalitu kódu nad rámec funkční korektnosti
(udržovatelnost, čistota) a~efektivitu (spotřeba zdrojů) současně.
Tato mezera naznačuje potřebu metrického rámce, který by
dimenze procesu, kvality kódu a~efektivity pokrýval současně.
Návrh takového rámce a~jeho operacionalizaci v~kontextu této
práce popisuje kapitola~\ref{kap:metodika}.

\paragraph{LLM-as-judge.}
Některé dimenze kvality, jako srozumitelnost commit zpráv, kvalita
dokumentace nebo vhodnost návrhových vzorů, nelze spolehlivě hodnotit
deterministickými nástroji. Jedním z~přístupů je využití LLM jako
hodnotitele (\textit{LLM-as-judge}). Zheng et al.~\cite{zheng2023mtbench}
ukázali, že LLM dokáže hodnotit kvalitu výstupů na úrovni
srovnatelné s~lidskými hodnotiteli, ale identifikovali tři
systematické biasy: \textit{position bias} (preferuje odpověď
na určité pozici), \textit{verbosity bias} (preferuje delší
odpovědi) a~\textit{self-enhancement bias} (preferuje vlastní
výstupy). Panickssery et al.~\cite{panickssery2024} prokázali
korelaci mezi schopností modelu rozpoznat vlastní výstupy a~mírou,
do jaké je preferuje, což naznačuje kauzální vztah mezi
self-recognition a~self-preference. Verga et al.~\cite{verga2024poll}
navrhli mitigaci formou panelu diverzních modelů (PoLL), který
dosahuje lepší shody s~lidským hodnocením než jednotlivý model.
Praktickou implikací je volba hodnotícího modelu z~odlišné modelové
rodiny, než ve které pracuje hodnocený agent.

\paragraph{Test oracle problem.}
S~testováním souvisí \textit{test oracle problem}: kdo definuje
správný výsledek? Mathews et al.~\cite{mathews2024} zjistili, že
nástroje pro automatické generování testů systematicky filtrují
selhávající testy; až 68,1\,\% výsledných testovacích sad validuje
chybné chování místo jeho odhalení. Chen et al.~\cite{rethinking2025}
na 500~úlohách benchmarku SWE-bench Verified potvrdili, že
agent-generované testy slouží primárně jako observační zpětná vazba,
nikoli jako validační nástroj. Obranou proti tomuto problému je
odvozování očekávaných hodnot ze specifikace, nikoli z~pozorování
kódu.

Benchmarky i~doplňkové mechanismy z~této sekce hodnotí
převážně izolované úlohy a~jednotlivé aspekty výstupu. Pro
vyhodnocení agenta v~kontextu jedné case study je třeba metrik
pokrývajících dimenze produktu, procesu i~zdrojů současně;
jejich návrh je obsahem kapitoly~\ref{kap:metodika}.

\textbf{Fine-tuning vs in-context learning:}

Dva přístupy jak přizpůsobit LLM konkrétnímu úkolu:
\begin{itemize}
    \item \textbf{Fine-tuning}: trénování parametrů modelu. Permanentní, drahé.

\textbf{Narativní flow (revidovaný):}
\begin{enumerate}
    \item \textbf{Složitost systémů roste} -- software je čím dál komplexnější
          \\ → \texttt{sommerville2016} s.~582:
          \\ \textit{``The root cause of these problems is, as it was in the 1960s, that we are trying to build systems that are larger and more complex than before. We are attempting to build these `mega-systems' using methods and technology that were never designed for this purpose.''}

    \item \textbf{Abstrakce jako nástroj} -- reakce na složitost:
    \begin{itemize}
        \item Assembler → C → Java → frameworky
        \item Každá vrstva skrývá detaily (information hiding)
              \\ → \texttt{colburn2000} s.~1:
              \\ \textit{``Abstraction through information hiding is a primary factor in computer science progress and success through an examination of the ubiquitous role of information hiding in programming languages, operating systems, network architecture, and design patterns.''}
        \item Dijkstra: abstrakce pomáhá být přesný, ne vágní
              \\ → \texttt{swebok2024} s.~370
    \end{itemize}

    \item \textbf{Přesto 1968 krize} -- proč?
    \begin{itemize}
        \item Složitost rostla rychleji než naše schopnost ji zvládat
        \item NATO konference: ``software crisis''
              \\ → \texttt{nato1968} s.~78 (Perlis keynote):
              \\ \textit{``I believe it is because we recognize that a practical problem of considerable difficulty and importance has arisen: The successful design, production and maintenance of useful software systems.''}
    \end{itemize}

    \item \textbf{Reakce: vznik SWE} -- disciplína pro řízení složitosti
          \\ → \texttt{sommerville2016} s.~592:
          \\ \textit{``In software engineering, we have seen the incredibly rapid development of the discipline to help manage the increasing size and complexity of software systems... the approach that has been the basis of complexity management in software engineering is called reductionism.''}

    \item \textbf{Dnes: AI jako nový problém}
    \begin{itemize}
        \item Není to jen další vrstva abstrakce
        \item Je to ztráta determinismu -- ``black box''
        \item Proto mechanistic interpretability
              \\ → \texttt{bereska2024} s.~1:
              \\ \textit{``Understanding AI systems' inner workings is critical for ensuring value alignment and safety.''}
    \end{itemize}
\end{enumerate}

\textbf{Klíčový insight:}
Abstrakce $\neq$ složitost. Abstrakce je NÁSTROJ pro zvládání složitosti.
AI přináší kvalitativně nový problém (nedeterminismus), ne jen ``více abstrakce''.

\textbf{1. SWE je fundamentálně týmová disciplína}

\textbf{Brooks's Law -- komunikační overhead:}
\par\noindent → \texttt{brooks1975} s.~25:
\par\noindent \textit{``Adding manpower to a late software project makes it later.''}
\par\noindent → \texttt{mcconnell2004} s.~713:
\par\noindent \textit{``Merely increasing the number of people increases the complexity and amount of project communication.''}
\par\noindent Komunikační kanály rostou: $n(n-1)/2$

\rule{\textwidth}{0.4pt}

\textbf{2. Role a zodpovědnosti}

\textbf{Tradiční role:}
Developer, Tester/QA, Architekt, Project Manager, Product Owner.

\textbf{Role v Scrum:}
\par\noindent → \texttt{scrumguide2020}:
Product Owner, Scrum Master, Developers.

\rule{\textwidth}{0.4pt}

\textbf{3. Conway's Law -- organizace $\leftrightarrow$ architektura}

\par\noindent → \texttt{conway1968}:
\par\noindent \textit{``Organizations which design systems are constrained to produce designs which are copies of the communication structures of these organizations.''}

\rule{\textwidth}{0.4pt}

\textbf{4. Koordinace práce}

\par\noindent → \texttt{malone1994}:
\par\noindent Coordination = managing dependencies between activities.
\par\noindent Typy závislostí: shared resources, producer-consumer, simultaneity constraints.

\textbf{Tacit vs explicit knowledge:}
\par\noindent → \texttt{nonaka1995}:
\par\noindent \textit{``There are two types of knowledge: explicit knowledge, contained in manuals and procedures, and tacit knowledge, learned only by experience, and communicated only indirectly.''}

\begin{itemize}
    \item \textbf{Tacit knowledge} -- v hlavách lidí, těžko artikulovatelné
    \item \textbf{Explicit knowledge} -- dokumentace, procesy, kód
    \item Konverze tacit → explicit = klíčový proces (externalization)
\end{itemize}

\rule{\textwidth}{0.4pt}

\textbf{Quality gates pro agenty:}
\begin{itemize}
    \item Agent přebírá některé role (developer, částečně tester)
    \item Quality gates zůstávají -- kdo je teď dělá?
    \item Implicitní znalosti z meetingů $\rightarrow$ explicitní instrukce pro agenta
\end{itemize}

\textbf{1. Artefakty podle fází:}

\begin{itemize}
    \item \textbf{Specification} $\rightarrow$ Requirements, user stories, use cases, behavioral models
          \par Spektrum formátů: Formální (IEEE 830), Structured (šablony), Semi-structured (GitHub Issues), Neformální (konverzace)
          \par V open source: issue trackery jako de facto requirements management \cite{scacchi2002}
          \par V agilních týmech: user stories místo SRS \cite{cao2008}
    \item \textbf{Design} $\rightarrow$ Architektura, design docs, diagramy, API kontrakty
    \item \textbf{Implementation} $\rightarrow$ Zdrojový kód, konfigurace
    \item \textbf{Validation} $\rightarrow$ Testy (unit, integration, e2e), test reports
    \item \textbf{Evolution} $\rightarrow$ Change requests, release notes, patches
\end{itemize}

\textbf{Traceability:}
\par\noindent → \texttt{gotel1994}:
\par\noindent \textit{``Requirements traceability refers to the ability to describe and follow the life of a requirement, in both a forwards and backwards direction.''}
\par\noindent Propojení: Requirement $\rightarrow$ Design $\rightarrow$ Code $\rightarrow$ Test.

\rule{\textwidth}{0.4pt}

\textbf{2. Nástroje podle činností:}

\begin{itemize}
    \item \textbf{Vývoj:} IDE (VS Code, IntelliJ), editory, debuggery
    \item \textbf{Verzování:} Git -- distribuovaný version control
          \par → \texttt{chacon2014}: ``everything as code''
    \item \textbf{Koordinace:} Issue tracking (Jira, GitHub Issues)
    \item \textbf{Kvalita:} CI/CD, test frameworks, linters
          \par → \texttt{humble2010}: automatizace buildů, testů, deploymentu
          \par → \texttt{forsgren2018}: DevOps praktiky a měřitelný dopad
    \item \textbf{Dokumentace:} Wikis, Markdown, generátory dokumentace
\end{itemize}

\rule{\textwidth}{0.4pt}

\textbf{3. Komunikační nástroje:}

\par\noindent → \texttt{schmidt1992} -- CSCW:
\par\noindent \textit{``Articulation work'' -- práce potřebná ke koordinaci spolupráce.}
\par\noindent Synchronní: Slack, Teams, meetings. Asynchronní: Email, code review, dokumentace.

\rule{\textwidth}{0.4pt}

\textbf{4. Standardy a formáty:}
UML \cite{fowler2004uml}, OpenAPI/Swagger, Markdown, JSON Schema, Conventional Commits.
