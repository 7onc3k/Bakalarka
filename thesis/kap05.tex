\section{Náměty pro další výzkum}

\begin{raw}
Future work.

\begin{itemize}
    \item Více modelů, více projektů
    \item Systematické porovnání formátů specifikace
    \item Multi-agent vs. single-agent scaffolding
    \item Longitudinální studie (více issues, evoluce projektu)
    \item \textbf{Proč agent nedodržuje multi-step workflow.} Pilotní data
          ukazují, že agent dodržuje verifikační příkazy (jednokrokové akce)
          deterministicky, ale multi-step workflow (issue~$\to$ branch~$\to$
          test~$\to$ PR) nedeterministicky --- r3 dodržel kompletně, r5 zcela
          ignoroval při téměř identických instrukcích. Možné vysvětlení:
          (a)~jednoduché příkazy nevyžadují plánování, agent je kopíruje
          do terminálu; workflow vyžaduje udržet plán přes desítky kroků.
          (b)~Tréninková data modelu obsahují oba vzorce --- strukturovaný
          i~nestrukturovaný vývoj --- a~model mezi nimi volí stochasticky.
          (c)~Pozice instrukce v~kontextovém okně: s~rostoucí délkou konverzace
          klesá vliv dřívějších instrukcí. Granulární ablace workflow struktury
          (které kroky jsou kritické?) a~opakované běhy se stejnými instrukcemi
          by tento fenomén pomohly lépe pochopit.
    \item \textbf{Kontinuita práce mezi agenty.} Procesní metriky (P1--P8)
          měří transparentnost artefaktů --- issues, commit zprávy, PR popisy.
          Otevřená otázka: stačí tato transparentnost k~tomu, aby jiný agent
          (nebo člověk) navázal na rozpracovaný projekt? Testování handoff
          scénářů by ověřilo, zda procesní scaffolding vytváří nejen
          pozorovatelný, ale i~přenositelný pracovní kontext.
    \item \textbf{Automatizace iteračního postupu.} Fáze Diagnóza a~Úprava jsou
          v~této práci prováděny manuálně. Frameworky jako PromptWizard
          \cite{agarwal2024promptwizard} (Score→Critique→Synthesize) nebo
          Prompt Alchemy~\cite{promptalchemy2025} ukazují, že tento cyklus
          lze automatizovat --- model sám analyzuje kde instrukce selhaly
          a~navrhuje úpravy. Kombinace automatizovaného APO s~metrikami P/Q/E
          by umožnila rychlejší iteraci bez manuální diagnózy.
\end{itemize}
\end{raw}

\textbf{Pracovní závěr z pilot-r4 --- exit kritéria sama o sobě nestačí.}

Pilot-r4 zpřesnil, jak tento problém skutečně vypadá. Původní hypotéza byla,
že explicitní success criteria v~\texttt{AGENTS.md} mohla agenta přesměrovat
z~procesu na výsledek. Po obnovení session transcriptu se ale ukázalo něco
specifičtějšího: agent si prokazatelně načetl produktovou specifikaci z~Issue~\#1,
ale neaktivoval \texttt{AGENTS.md} jako operativní workflow. Prakticky to znamená,
že jeho skutečná pracovní smyčka nebyla ``issues $\rightarrow$ branch $\rightarrow$
test commit $\rightarrow$ implementation commit $\rightarrow$ PR'', ale pouze
``todo $\rightarrow$ write/edit $\rightarrow$ checks $\rightarrow$ done''.

Tento rozdíl je důležitý metodologicky. Nevidíme přímý důkaz, že by agent
explicitně použil success criterion ``all implementation issues are closed''
jako triviální zkratku typu ``žádné issues neexistují, tedy jsou zavřené''.
Taková úvaha v~transcriptu není. Vidíme ale přímý důkaz jiného mechanismu:
procesní instrukce nebyly převzaty jako řídicí smyčka běhu. Agent tedy neselhal
až při vykonávání workflow; workflow se vůbec nestalo jeho pracovní reprezentací
úkolu.

Pro návrh instrukcí z~toho plyne praktičtější závěr než původní úvaha
o samotných exit kritériích. Nestačí přidat ``jak poznáš, že jsi hotový''.
Je potřeba vynutit i~ověřitelný \textit{ingestion checkpoint} na začátku běhu:
agent musí explicitně potvrdit, že přečetl \texttt{AGENTS.md}, rozumí
procesním pravidlům a~před prvním zápisem kódu je aktivoval. Jinak hrozí,
že i~dobře formulované procesní instrukce zůstanou pouze pasivním kontextem,
zatímco skutečné řízení běhu převezme lokální implementační smyčka odvozená
ze specifikace.

Z~tohoto závěru přímo vychází návrh další iterace instrukcí. V~souladu
s~iteračním postupem zde není navržen balík nových guardrailů, ale jedna
minimální změna pro jeden problém. Globální blok ``You are done when'' je
odstraněn ze sekce Goal a~nahrazen jediným preflight checkpointem na začátku
Process, v~němž má agent explicitně potvrdit, že přečetl \texttt{AGENTS.md},
Issue~\#1 a~aktivuje workflow před prvním zápisem kódu. Cílem tedy není
rozšířit instrukci, ale přesunout důležitý signal z~globálního completion cue
do pozorovatelného workflow kroku.

to evidence, že problém r4 nebyl v~samotné existenci success criteria, ale
v~jejich umístění a~v~tom, že workflow nevstoupilo do první pracovní
reprezentace úkolu.

\textbf{Feature work / námět k diskuzi --- exit kritéria jako součást instrukcí:}

Otázka: co by se stalo kdybychom agentovi předali exit kritéria přímo v AGENTS.md?
(``Musíš dosáhnout P1=5/5, Q3$\geq$70\,\%, Q5=0 --- ověř si to před PR.'')

Argument PRO: pokud máme dostatečný počet metrik pokrývající různé dimenze (proces, kvalita, efektivita),
optimalizace na metriky = dobrá práce. Goodhartův zákon platí pro jednorozměrné metriky ---
agent který optimalizuje jen coverage může zanedbat kvalitu. Ale s 13 metrikami napříč P/Q/E
je těžší gaminovat všechny najednou bez skutečné kvality.

Argument PROTI: agent může najít zkratky (napr. trivální testy pro Q3, verbose kód pro Q7).
Také: explicitní metriky v instrukcích mění povahu experimentu --- měříme pak schopnost agenta
sledovat metriky, ne schopnost dodržovat vývojové praktiky.

Kompromis k prozkoumání: přidat do AGENTS.md jen deterministické quality gates jako self-check
(``Run tsc --noEmit before PR, run eslint src/ --- zero warnings required'') bez číselných prahů.
Agent ví co zkontrolovat, ale neví jaký je náš práh → nelze triválně optimalizovat.
\end{raw}
